# OpenLakeForge Technical Debt

This document tracks known OpenLakeForge weaknesses, current mitigations, and
the intended fix path. ADRs remain the historical decision log; this file is the
current technical debt backlog.

`Resolved` means resolved in OpenLakeForge, not merely fixed upstream. `Yes
(branch)` means the implementation and local migration validation are complete
on the current branch; its listed cloud acceptance work still has to pass before
the change is merged.

## OpenLakeForge-Owned Debt

These items can be fixed primarily in this repository without waiting for an
upstream project to change behavior.

| Weakness | Current Impact | Solution | Pending Work | Resolved |
| --- | --- | --- | --- | --- |
| Dynamic artifact revision drift is still possible outside the deploy flow. | A v0.3 `ProjectActivation` now records and injects `OPENLAKEFORGE_FLOE_MANIFEST_REVISION` into the stage user deployment, and its `ACTIVE.json` pointer advances only after the release rolls out. Manual image builds, manual bucket uploads, or direct Kubernetes edits can still make a legacy deployment disagree with its recorded revision. | Make status inspect the user deployment's image, labels, and revision environment in addition to the Helm release, and retire the deprecated single-DEV artifacts path once migration is complete. | #115 closes the activation-path drift; legacy compatibility and richer workload observation remain follow-up work. | No |
| `olf floe revision` and `olf project revision` publish through parallel content-addressing code. | `tools/olf/olf/revision.py` (v0.2 Floe runtime-artifact revision) and `tools/olf/olf/project_revision.py` (#154's `ProjectRevision`) both compute a sorted `key\0digest\n` aggregate hash and an immutable-write publish step; `artifact_store.py` only unified their bucket/client resolution, not the publish/verify logic itself. | Fold `olf/revision.py`'s manifest/publish/verify onto the shared `RevisionStore` primitives in `artifact_store.py`, keeping the two revisions' meanings distinct. | Not started; introduced by #154. | No |
| OpenMetadata metadata seeding is imperative. | Domain, data-product, medallion bucket containers, and table stub metadata are seeded through script-driven OpenMetadata REST calls; table stubs can diverge from crawler-discovered metadata. | Add stale managed asset reconciliation and post-crawl validation; prefer native OpenMetadata ingestion once the relevant connector issues are fixed. | Not started. | No |
| OpenMetadata Superset registration used an incomplete local payload. | Resolved: the bootstrap registers the Superset dashboard service with the nested API connection that OpenMetadata's ingestion SDK expects. OpenMetadata still only shows Superset reports after its dashboard metadata ingestion pipeline crawls Superset. | Keep the schema-aligned Superset connection payload in the bootstrap and trigger/crawl Superset metadata after report artifacts are imported. | Fixed in bootstrap; verified manually through the OpenMetadata Superset service connection and imports. | Yes |
| E2E readiness is weaker than the runtime it validates. | `olf e2e run --env local` can pass pod readiness while Dagster product gRPC locations are still unavailable, then fail a launch with GraphQL 500. Historical failed Dagster-run pods can also block preflight despite being unrelated to the current suite. | Gate on loadable Dagster repositories, retry bounded transient launch failures, and distinguish historical Jobs from jobs created by the suite. | Tracked in [#61](https://github.com/OpenLakeForge/openlakeforge/issues/61); preserve diagnostics and tests for persistent failures. | No |
| Live end-to-end validation is mostly manual. | Static checks can pass while runtime behavior across Dagster, Floe, dbt, Trino, Superset, and OpenMetadata regresses. | Keep all environments on the shared full e2e suite: run all product pipelines, verify Silver and Gold table counts, verify each Gold mart has rows, verify Superset dashboards, and verify OpenMetadata domains/data products. | `v0.1.0-alpha.1` requires recorded clean local release evidence. Fresh main/nightly local conformance is reopened as #60 for `v0.2-alpha`; AWS remains a later profile gate. | No |
| Repository checks had split Python and shell ownership. | Resolved: `olf check` owns structure, component, contract, infrastructure, project-code, dbt, and lockfile checks; the structural check rejects tracked shell scripts. | Keep behavioral tests alongside the Python command services. | Delivered with ADR 0008 and issue #126. | Yes |
| Removing a stage with `--allow-stage-removal` leaves its Polaris principals and shared Trino Secret behind. | The Polaris bootstrap job now rotates a stage-scoped (Floe/deployer) principal's credentials instead of failing when its namespace-recreated Secret is missing, so re-enabling a removed stage reconnects per ADR 0002. The stage's Polaris principals themselves, and its Trino credential Secret in the shared namespace (`$NAMESPACE`), are never proactively revoked on removal - they sit unused until the stage returns. | Add an explicit teardown step, gated by the same `--allow-stage-removal` opt-in, that revokes a removed stage's three Polaris principals and deletes its shared-namespace Trino Secret via the Polaris admin API. | Not started; flagged as a PR #163 review finding. Low risk today: the orphaned identities are inert until a matching stage namespace exists again. | No |
| Cloud artifact deploy temporarily mutates `os.environ` to reach in-process AWS clients. | `olf.deployment.cloud.artifacts._applied_authentication_environment` overlays selected AWS credential-selection variables onto `os.environ` for the duration of the artifacts phase, because `GlueClient`, `s3.upload_direct`, and `revision._artifact_storage_client` construct their boto3 clients from `os.environ` directly rather than accepting the deployment's command environment. This contradicts `DeploymentContext.command_env`'s documented invariant of never mutating `os.environ`, and is only safe because `olf deploy` runs these phases sequentially in one process. | Thread the resolved AWS session (or its credential-selection environment) explicitly into `GlueClient`, `s3.upload_direct`, and `revision._artifact_storage_client` instead of relying on a process-wide overlay. | Not started; introduced by ADR 0008's SDK-managed authentication. | No |
| Provider contracts retain a v2 reader for pre-v0.3 platform state. | Every root (local, AWS, Azure) now emits a native v3 stage index and stage consumers resolve it directly. The v2 reader (`tools/olf/olf/provider_contracts/_v2.py`) still exists to parse contracts from state predating this rollout. | Remove the v2 reader once no supported deployment can still emit it, with the documented platform-first migration. | #114. | Yes |
| Cloud stage runtimes still resolve a single data plane. | Local, AWS, and Azure now each give every enabled stage distinct medallion buckets/tables, a stage-owned credential identity, and a Trino catalog. AWS cannot create a native Glue catalog per stage in this account, so every AWS stage instead shares the account's one default catalog with a `namespace_prefix` on physical database/schema names (Trino `tables` access rules add a second enforcement layer on top of IAM's `database/<prefix>_*` scoping). Verified end-to-end against a live AWS account; Azure is `terraform validate`/`plan`-verified only (no live subscription available). | Live-verify the Azure POC root against a real AKS subscription. | #114. | Yes |
| Trino has no client authentication. | Every stage-scoped client (dbt, Dagster's runtime, Superset, the e2e suite) is granted or denied catalog/table access by the `X-Trino-User` value it sends, which Trino accepts unauthenticated - any workload able to reach the shared Trino service can claim `olf-prod-runtime` and receive PROD's catalog access. Real isolation on AWS currently comes from IAM's `database/<prefix>_*` scoping on the underlying Glue catalog, not from Trino's own access-control rules, which are a soft, defense-in-depth boundary only. | Enable real Trino authentication (e.g. OAuth2/OIDC or mTLS) and bind each stage's principal to a verified identity before trusting the username in `catalog_access_rules`/`tables` rules. | Not started; flagged in PR #163 review. | No |
| Floe manifests/revisions/reports are shared, not stage-scoped, S3/object-storage prefixes. | `olf.revision`/Floe's own per-domain config (`lakehouse_code/*/contracts/floe/*.yml`'s `path: "floe/reports/<domain>"`) deliberately publish at the ops bucket root, independent of any stage's `activations/<stage>` prefix (`project_code_check.py` asserts this exact shape) - "a revision is not an activation." Every stage's credential is therefore granted read (and, for reports, write) access to these same bucket-root prefixes, so a DEV identity can read PROD's published manifests/revisions and read+overwrite PROD's Floe run reports for a shared domain. This is intentional (the grant that removing it would break is load-bearing, verified live against a real deploy), not an oversight. | Give reports a stage or run-scoped key (or a separate write-once/versioned prefix per stage) so no stage identity needs write access to another stage's report history; keep manifests/revisions shared by design. | Not started; flagged in PR #163 review. | No |
| A loop or local variable is reused under a second type in one scope. | Resolved: `olf/superset.py:180` (`path`: `Path` then `PurePosixPath`), `olf/commands/artifacts.py:96` (`root`: `Path` then `str`), `olf/e2e/_health.py:118` (`diagnostics`: `str` then `list[str]`) and `olf/scaffold/_commit.py:121` (`table`: `SilverTable` then `Table`) each made the second half of its function unsafe to edit against the type the first half established -- the exact failure mode of a large generated change. Each second binding is renamed, and every `olf` module is now type-checked, so mypy rejects a new one as an incompatible assignment. | Rename the second binding. | None: `_commit.py`, `artifacts.py` and `_health.py` were fixed in #290, `superset.py` before the override list was emptied in #288. | Yes |

## Upstream-Related Debt

These items are caused by external project behavior or need upstream acceptance
before OpenLakeForge can remove its workaround cleanly.

| Weakness | Current Impact | Solution | Pending Work | Resolved |
| --- | --- | --- | --- | --- |
| DuckDB Gold replacement was non-atomic. | Resolved in `main`: dbt-trino uses Trino Iceberg `CREATE OR REPLACE TABLE` with `on_table_exists: replace`, preserving the previous snapshot on failed replacement. | Keep the Trino atomic-replacement regression test in the migration gate. | Local validation passed; AWS remains a later compatibility gate. | Yes |
| DuckDB Glue location/UDF/orphan workaround. | Resolved in `main` by routing all Gold writes through the existing Trino Glue Iceberg connector; DuckDB plugin, NumPy dependency, direct Glue REST creation, and custom UDF are removed. | Keep AWS Glue location and referenced-file inventory checks in the migration gate. | Local validation passed; validate the full AWS product suite in the AWS reference-profile gate. | Yes |
| Superset handling of Trino/Iceberg metadata fields breaks table preview. | Superset's Trino engine spec treats Trino Iceberg `$partitions` metadata fields as table partition columns and can generate invalid SQL Lab preview filters. | Upstream a Superset `TrinoEngineSpec` fix to ignore Iceberg `$partitions` metadata fields as real partition filters; once released, remove `patch_trino_iceberg_partitions.py` and retest preview through Trino. | PR [apache/superset#41055](https://github.com/apache/superset/pull/41055) is open and requires at least one approving review. | No |
| Superset still requires a custom image. | The stack cannot use the official Superset image directly because the local image installs Trino/PostgreSQL drivers and applies the Trino/Iceberg preview patch. | Remove the source patch after the upstream Superset fix; then decide whether drivers remain in a minimal project image, a chart-supported install path, or an official image variant. | Blocked by the Superset Trino/Iceberg patch being merged and released. | No |
| Floe manifest replay omitted dataset context from OpenLineage events. | Resolved: Floe 0.6.11 passes manifest entities to the runtime lineage observer, while OpenLakeForge emits resolved source URIs and supplies the OpenMetadata JWT only through the runner's Kubernetes Secret reference. OpenMetadata now resolves the complete Bronze→Silver→Gold graph. | Keep Floe at 0.6.11 or later, retain `resolved-uri` manifest generation, and keep credentials out of generated manifests. | Fixed by [malon64/floe#455](https://github.com/malon64/floe/issues/455) and released in [Floe 0.6.11](https://github.com/malon64/floe/releases/tag/v0.6.11). Local acceptance verified all 15 Bronze→Silver edges and complete upstream graphs for all 9 Gold marts. | Yes |
| `openlineage-dbt` + `dbt-duckdb` resolves datasets under the DuckDB file namespace. | Resolved for Gold in `main`: dbt-trino emits `trino://host:port` dataset namespaces that map to the canonical Iceberg service. | Keep the captured event and OpenMetadata entity-resolution test. | Local validation passed; include AWS OpenMetadata entity resolution in the AWS reference-profile gate. | Yes |
| OpenMetadata Dagster connector is deferred. | The Dagster pipeline service and ingestion pipeline are registered but not triggered because the OpenMetadata connector uses the deprecated `PipelineRuns` GraphQL type while Dagster 1.x uses `Runs`. This is still present in OpenMetadata `1.13.6-release`, the version OpenLakeForge pins. | Open an upstream OpenMetadata issue or patch the connector to use the current Dagster GraphQL schema, then trigger the pre-registered ingestion pipeline and validate pipeline metadata. | Not started. | No |
| OpenMetadata Polaris OAuth handling needs a workaround. | Resolved: OpenMetadata 1.13 removed its Iceberg connector, and the lakehouse service now crawls through Trino, so OpenMetadata no longer connects to Polaris or needs a Polaris token. | None. | Removed with the move to OpenMetadata 1.13.6 (#131). | Yes |
| Floe manifest replay did not preserve S3 storage definitions for AWS runs. | Resolved: OpenLakeForge uses Floe-generated manifests and no longer rewrites them to run with `-c <config-uri> -p <profile-uri>`. AWS artifact deployment publishes only Floe-generated manifests. | Keep manifest generation owned by Floe; do not add post-generation JSON mutation in OpenLakeForge. | Fixed by [malon64/floe#425](https://github.com/malon64/floe/issues/425) and consumed through the configured Floe runner image. | Yes |
| Floe Iceberg S3 writes did not use EKS Pod Identity container credentials. | Resolved upstream; OpenLakeForge now points AWS runner manifests at the configured Floe image. | Continue using EKS Pod Identity for AWS Floe runner pods. | Fixed by [malon64/floe#426](https://github.com/malon64/floe/issues/426). AWS end-to-end validation remains tracked under the rollout gate below. | Yes |

## POC/Production Hardening Debt

These are OpenLakeForge-owned hardening items. They are separated from the
runtime bugs above because they mostly affect operational maturity.

| Weakness | Current Impact | Solution | Pending Work | Resolved |
| --- | --- | --- | --- | --- |
| Stateful services run in-cluster. | Local and Azure POC profiles run SeaweedFS, PostgreSQL, OpenSearch, Redis, Polaris, Dagster, OpenMetadata, Trino, and Superset inside Kubernetes without production-grade durability controls. Polaris catalog state now survives Polaris pod restarts through the shared PostgreSQL service. | Replace stateful dependencies with managed or hardened services where appropriate: managed PostgreSQL, durable object storage, backups, resource limits, storage classes, and disaster recovery. | Polaris restart recovery is implemented. PostgreSQL and the remaining in-cluster stateful services still lack production backups, HA, and disaster recovery. | No |
| Secrets and Terraform state are development-grade. | Local Terraform state and Kubernetes Secrets carry generated development credentials. | Use encrypted remote state, Key Vault or another external secret backend, External Secrets Operator, secret rotation, and reference-only Terraform outputs. | Not started. | No |
| Terraform state holds the generated credential values, including the identity client secrets. | Every `random_password` (SeaweedFS S3, Polaris root, PostgreSQL, Superset) is stored in plaintext in Terraform state next to the Kubernetes Secret it fills, and the Keycloak adapter's client secrets and bootstrap admin password join them. `olf check contracts` (#181) fails if a root output is sensitive or unwraps a secret, or if an applied provider contract carries a secret value, so state is the only place the values live outside the cluster. On local and on-premises the state sits on the operator's workstation beside a cluster-admin kubeconfig that already reads every Secret, so this adds no privilege and is accepted for v0.5-alpha. Cloud state is worse: AWS has no remote state yet (#132). | Encrypted remote state with locking (#43, #132), then External Secrets Operator so Terraform stops generating credential values; identity client secrets are minted by the issuer or a bootstrap job where practical. | Cloud: closes in v0.9-beta with remote state and External Secrets (AWS remote state is scheduled for v0.6-beta). Local and on-premises: stays open, since the workstation-local state is the accepted model until a managed secret backend is adopted there. Identity client secret rotation: `docs/setup/identity-secret-rotation.md`. | No |
| Access is port-forward based. | Local and Azure POC access uses `kubectl port-forward` with no ingress, DNS, TLS, SSO, or public/private endpoint policy. | Implement the `access.ingress` adapter (Traefik, cert-manager, local CA), stage-derived routes and local trust, then OIDC/SSO for Superset and OpenMetadata. | Contract defined (ADR 0013, #264); local Traefik/cert-manager adapter and local CA installed (#265); local routes emitted (#266); trust and preflight pending (#267, #268); SSO in v0.5. | No |
| SeaweedFS built-in UIs are local-dev only. | The Filer and Master UIs help inspect local object storage but are exposed only by localhost port-forward and are not secured by ingress, TLS, SSO, or fine-grained read-only policy. | Keep them as local inspection tools; for shared environments, add proper identity/access policy or replace them with provider-native object storage console access. | Local port-forward support implemented; production access model deferred. | No |
| Full observability stack is deferred. | Logs, Floe reports, dbt artifacts, and Dagster compute logs are archived to `openlakeforge-ops`, but there is no Loki/Grafana query UI, Prometheus metrics, tracing, or alerting. | Keep `observability.object_log_archive` as the hardened processing baseline, then add Loki/Grafana or provider-native logging behind a future observability adapter. | Object archive implemented; query UI/metrics/tracing not started. | No |
| Floe profile variables and remote path resolution needed rendered AWS configs. | Resolved: domain Floe configs now use profile variables for bucket and region values, and OpenLakeForge removed the local config renderer. | Keep provider-specific values in Floe profiles and let Floe render manifests from config/profile inputs. | Fixed by [malon64/floe#424](https://github.com/malon64/floe/issues/424) and consumed through the configured Floe runner image. | Yes |
| AWS Glue/S3 writer compatibility is a rollout gate. | The AWS profile now provisions EKS/ECR, S3, RDS PostgreSQL, Glue, and EKS Pod Identity, but Floe and dbt-trino writes through Glue/S3 still need live proof before the AWS POC is considered complete. | Keep Trino as the first AWS query path and run a focused compatibility test: one Floe Silver write and one dbt-trino Gold write into Glue/S3, then query both through Trino. | Floe Silver write+read through Glue has been proven. Pending: a green Dagster dbt-trino Gold run, Trino query of both layers, Gold replacement/referenced-file checks, and OpenMetadata crawl/entity resolution. | No |
| Cloud provider adapters are still POC-level. | Azure uses AKS and ACR but keeps SeaweedFS, Polaris, PostgreSQL, Kubernetes Secrets, and port-forward access. AWS replaces storage, metadata PostgreSQL, and catalog with managed services, but still uses local state, Kubernetes Secrets, port-forward access, and no Lake Formation. | Promote each provider dependency behind explicit contracts: remote state, external secret managers, workload identity-only app auth, ingress/private access, TLS, backups, and observability. | Azure managed services and AWS production hardening are still pending. | No |
| Local image distribution is fragile. | kind image loading, large image pulls, and corporate TLS interception can make first-run setup brittle. | Prefer registry-published images for non-local targets, pin heavy runtime image versions or digests, and document CA trust bootstrap for constrained networks. | Not started. | No |
| Cloud and local orchestration had shell remnants. | Resolved: `olf` owns local, AWS, and Azure lifecycle commands, image handling, Floe generation, diagnostics, and smoke sequencing; Kind remains a local-provider prerequisite. | Keep provider-specific differences behind the Python provider adapter seam. | Delivered with ADR 0008 and issue #126. | Yes |
